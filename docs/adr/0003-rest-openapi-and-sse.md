# ADR 0003：REST、OpenAPI 与 SSE

- 状态：Accepted
- 日期：2026-09-02

## 背景

Studio、自动化客户端和后台任务需要稳定的资源接口与进度推送。当前不实施多人实时协同编辑，也没有证据支持引入多种公共 API 风格。

## 决策

- 公共 HTTP 接口使用 `/api/v1` 下的资源型 REST。
- FastAPI 生成的 OpenAPI 文档是 API 契约源，`packages/api-client/` 由该契约生成，不手写重复 DTO。
- 长任务进度使用 SSE。事件必须包含稳定事件 ID、关联 ID、任务 ID 和可恢复游标；客户端断线后可从最后事件继续。
- 错误、分页、幂等键、关联 ID 和请求追踪使用统一公共契约，并由契约测试锁定。
- 写请求在语义适合时支持幂等键；重试不得产生重复资源或重复任务。
- 协同编辑 WebSocket 延后到有明确并发编辑需求和冲突模型之后。

## 替代方案

### GraphQL 作为首要接口

暂不采用。第一版资源和工作流边界可由 REST 清晰表达，引入另一套模式和授权面没有必要。

### WebSocket 承载所有进度

拒绝。单向服务端事件更适合 SSE，断线恢复和 HTTP 基础设施也更简单。

### 手写前后端类型

拒绝。重复定义会产生漂移；客户端必须由已验证的 OpenAPI 生成。

## 后果

### 正向

- 接口可发现、可生成、可做快照和契约测试。
- 进度通道保持简单，同时具备断线恢复语义。
- API 版本边界清晰，便于未来兼容迁移。

### 代价与风险

- OpenAPI 变更必须同步再生成客户端并审查差异。
- SSE 需要代理缓冲、心跳和连接上限的运行配置。
- 若未来加入协同编辑，需要单独 ADR 定义一致性和冲突解决模型。
