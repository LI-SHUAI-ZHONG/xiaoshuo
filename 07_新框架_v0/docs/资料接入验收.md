## 资料工作流

在同一个 workspace 内准备冻结的 `materials/catalog.db`、网络身份对账和已托管的项目。使用 `materials route <id>` 取得 `source.id`、`source.file_sha256` 和 `source.sha256`。使用 `materials show <id>` 回读原文，再把适用于当前设计的具体位置写入设计请求。重复编号要先区分来源版本。

设计请求在原有 `mode`、`design_scope`、`budget` 之外，可带 `materials` 数组。每条都要有上面的三个来源字段、`disposition` 和 `reason`。处置取 `required`、`deferred` 或 `not_applicable`。全局路由记录资料的待审状态。项目资格由准确的源版本、核读结论、适用依赖和作者选定的设计共同确定。资料冲突、断边、未核读或字段不全的必用项会报出来源和拦截原因。

1. 用 `novel start --request design.json` 建任务，再用 `novel resume --job ID` 提取书级候选。用返回的步骤和令牌，按 README 的作者决定格式选定方向。
2. 审查并确认卷、章或场景方案。每项必用资料在细化范围内至少分配一场。其余场可逐项记延后或未适用及理由。若作者决定某个已采用条目在整个细化范围延后，设计请求可在 `material_deferrals` 中以来源 ID 为键记录理由。静态边绑定项目中的人物和悬念，动态边引用对应静态边并给出触发、选择、代价和世界及知情的前后状态。锚点记录同场 POV、物件和观察时机。选用 128.4 和 127.5 时，检查具体来源、选择理由、参数、可观察表现和验收点。细化可用 `parent_id` 继承已应用方向，并为当前阶段增加资料。
3. 写作请求用 `mode: write` 和应用结果里的 `scene_ids`。续写可用 `mode: continue`，由分支选取下一场。写作包只取本场适用且经作者核对的可见指令，必用项超出预算时停止。跨章 106.1 仅在有前章冻结稿的适用场景启用，首章可留待后续设计添加。
4. 审稿逐项返回通过、失败或未验证，附当前稿 ID、版本、哈希、精确 Unicode 半开区间、原文和理由。动态项的获批状态目标及已引用段落冻结为待验证输入，由独立状态提取核对同段证据。106.1 另查前章冻结叙述，相关前章原文只交给审稿。修订产生新版本并重新审查。
5. `batch:confirm` 展示当前稿、状态变化和逐项证据。作者确认后，接受事务再次核对来源、适用绑定、当前稿、审稿及状态证据，再推进接受指针和故事状态。重开后用 `novel show --job ID` 回查，并用 `novel resume` 继续。已经保存的模型结果不会重发。

范围决定以所选设计为单位，后续设计继承其来源和书级承诺。资料改版或决定变更时，为受影响阶段重新设计和冻结。适用场景之间差异较大时，分别细化并逐项给出处置理由。语义判断来自独立审稿及作者核对，精确引用与状态匹配由程序核对。材料绑定的隔离工程验收与 M10 真实试写分别记录。

2026-11-05 隔离验收使用真实冻结目录的副本。两章两场接受，场景资料检查分别为 6 项和 4 项。首场关卡后重开继续，新增请求 0 次。先行反例缺 WORLD 状态变化，停在接受之前。全量回归 202 项通过。全量路由仍覆盖 23 个版本、781,216 个位置，其中已核读 12 个。待审来源与端点继续按 F2 台账复核。M10 仍为 IN_PROGRESS。
