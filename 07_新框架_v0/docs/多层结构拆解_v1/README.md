# 第 3 步：参考作品的多层结构拆解

日期：2026-11-20。范围：参考作品原文 → 全局结构 → 卷章场观察 → 跨章关系 → 有来源的方法草稿。工程验收结果见 [实际验收记录](03_实际验收记录.md)。

这一步解决“把局部短文条目累加当作完整剧情”的问题。新流程先通读全部已导入文本，整合主线、人物变化、因果及信息兑现的全书总览；章场细拆必须带着冻结的全局依据运行；最后逐类检查跨章关系。方法只能从作者批准的结构提炼，并保留所依据的结构版本、实际事件、关系和原文位置。

本轮没有把方法自动变成本项目的剧情卡、人物卡或章纲。实际项目前置筛选、卡片实例化、下游采用回执属于第 4 步。完整参考作品、真实模型和作者文学评价属于第 5 步。

## 客户端操作

1. 预存库导入参考作品，确认作品类型。已分类作品详情默认打开新的结构页面；侧栏仍可访问旧局部拆解及其记录。
2. 核对参考文本是完整作品、摘录，还是完整性未知，并说明判断依据。程序不会按篇幅、章数或模型判断替作者宣布原作完整。
3. 选择“多层自动拆解”，设置每段字符数、调用次数上限和完整输入预算。沿用设置中的通用兼容 API 与 `decompose` 阶段配置；没有可用配置时明确返回 `CONFIG_REQUIRED`。也可以从“人工建立目录”开始，以真实原文逐项维护。
4. 在全书总览、卷章场目录、人物与归并、事件因果节点、线索与人物弧光、跨章关系、原作证据、制作职责核对之间检查。钩子/伏笔/节奏分布显示当前已登记的引入、回应、埋设、提示、回收和情绪前后，不生成类型配额。
5. 编辑一条记录会新增整个结构版本，旧版、旧批准与调用记录保留。审核前须检查来源、范围、引用、跨章端点证据、阅读覆盖及待核实项；结构检查不代替作者判断。
6. 批准结构后，选择实际线索/弧光自动提炼方法，或建立手工方法草稿。自动结果也只是草稿；手工入口只保留依据，不会合成操作说明。到类型资料库补齐并独立审核八类要求。

## 交付内容

- [运行顺序与边界](01_运行顺序与边界.md)：全局优先、上下文携带、中断/预算、来源与审核。
- [数据结构与接口](02_数据结构与接口.md)：六张新增表、事件/线索字段、API、方法来源、Git 快照。
- [实际验收记录](03_实际验收记录.md)：真实执行的工程测试、隔离浏览器、正式库及保护核验。

核心实现是 `src/nw/studio/corpus_*.py` 与同名客户端模块；可移植界面验证入口是 `tools/serve_corpus_fixture.py` 和 `tools/check_corpus_ui.cjs`。测试夹具统一标 `[FAKE]`，位于隔离 `build/` 或 pytest 临时工作区。

## 仍须用实际作品验证

读完全部已导入字符，只能证明处理范围，不证明原作完整、所有线索已找全、分析正确或方法有创作价值。长篇中的分线合并、非线性时序、复杂人物身份与跨卷兑现必须审读。没有实际观察时应记录未观察或存疑，不能为凑七类结构捏造事件。

正式库尚无参考作品或拆解方法，本轮没有调用真实模型，也没有生成或批准正式正文。下一步是把经审核的方法按本项目已批准前置转成具体设计卡；最后再以完整作品和连续章节检验文学效果。
