# 小说制作步骤与类型资料库审计

审计日期：2026-11-19（America/New_York）。状态：DONE（本轮接口与供给审计，专项回归 81 passed；语义全量核定与真实文学验收仍 IN_PROGRESS）。

这是对现有实现的审计。本轮不修改制作流程、资料原件或数据库结构，不生成正式小说，不调用真实模型。审计工具只读取源码、只读查询现有数据库，并生成本目录的报告。报告和工具保存在同一 GitHub 仓库内。

## 结论

**当前不能认定“类型资料库已经能够完整支撑精细剧情、大纲以及整套制作步骤”。** 现有底层已经有十四阶段、明确前置、版本化人物/剧情/卷章场/伏笔卡，以及部分读者信息、伏笔和状态检查；新增拆解层却主要提供选项、步骤标签、用法短文和单处证据。两者的粒度和校验方式不一致。

优先核实的事实：

1. `book` 的现行定义明确是“只提方向，chapters 为空”。存在卷、章、场卡种，并不等于已经生成了覆盖全书的详细大纲。作者所要求的全书—分卷—连续章纲覆盖，需要另行定义、编排和验证。
2. 正式书库有 0 本参考作品、0 条拆解、0 条升级候选和 0 条采用记录。类型知识库有 0 条人工维护记录；类型定义仍可回退显示原类型表。717 个可选项是分类与方法选项，不是 717 份拆解经验。
3. 拆解默认映射只覆盖十四设计阶段中的七个。其余阶段允许显式指定，但没有默认供给入口。`structure` 和 `hook` 的拆解默认落点与向导偏好落点还不一致。
4. 自动拆解每次独立处理最多 12,400 字符、步进 12,000 字符的摘录，输出局部用法条目；当前没有显式的全书结构整合步骤，也没有跨章因果、钩子接力和伏笔生命周期数据对象。
5. 拆解参考按选项、类型匹配后冻结，进入 `author_input`。它有批准、来源、步骤和长度检查，但没有像原资料那样强制提交逐条前置引用、设计产物路径和下游执行回执。
6. 类型资料库选项只取自部分步骤文件。例如钩子来自“情节机制”和“读者追读”，结构来自“叙事结构”和 41–44 板块；伏笔专用、章节承接、事件、动作和状态传播等已有资料没有完整成为独立拆解选项。

因此，下一阶段应围绕既有消费者的真实需求重构拆解与调度，而不是仅增加分类名称、推荐数量或自由文本描述。

## 已确认可复用的基础

- 十四阶段的前置依赖、输入版本哈希及缺输入等待机制。
- 人物、世界、剧情、卷、章、场景、伏笔等不可变卡片及作者批准记录。
- 当前任务与上游产物参与原资料召回；部分原义条款可以指向真实输入、产物和指定下游，并要求下游执行回执。
- 人物状态、能力边界、关系、实际事件、选择、代价与后果的校验。
- `reader_plan`、`promise_plan`、回收窗口、伏笔状态及范围审稿的部分指标。
- 独立审稿、状态变更证据、作者接受和版本失效守卫。

这些是工程基础，不是文学效果已通过的证明。卡片字段和引用存在，也不能单独证明设计细致或原义使用正确。

## 对下一阶段的要求

先定义“本步需求—方法前置—可迁移操作—真实项目产物—指定消费者—验收证据”，再确定新表与界面。区分原资料规则、参考作品中的观察、归纳出的可复用方法、本项目的设计实例。保留来源与版本，给出不适用条件；缺义先明确登记，不能由模型假装原件已经提供。
