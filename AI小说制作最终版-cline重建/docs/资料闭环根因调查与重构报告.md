# 资料闭环根因调查与重构报告

## 1. 结论摘要

本次调查确认，系统的主故障不是原始资料数量过大，而是“资料存在”与“资料可执行”之间缺少运行层。工作区此前拥有规则、索引、模块关系、状态契约和项目中间文件，但它们主要以 Markdown、YAML、JSON 约定存在；没有独立执行器把任务转换为资料计划，把多模块结果合并为唯一综合决策，再把决策以可验证字段传到章节和正文。因此原有 `ERRORS=0` 只代表静态结构完整，不能证明创作能力已经生效。

本轮新增 `工具/运行资料闭环.ps1`，提供 `Audit`、`Plan`、`Verify` 三种模式。它在工作区边界内解析多维索引，读取项目上下文，计算任务相关模块，建立模块依赖边和执行顺序，生成证据与影响契约，并在验证模式检查章节执行清单和交接状态。规则、持续协议和系统检查器已接入该工具。

## 2. 实际系统运行方式（重构前）

1. Cline 读取 README、总规则和索引。
2. Cline 依据自然语言和索引说明手工选择模块。
3. Cline 读取若干原始资料或片段，并在对话中自行综合。
4. Cline 手工写入项目设计、章节执行清单、正文、快照和报告。
5. `工具/检查系统.ps1` 检查目录、路径、JSON 和关键词。

这个流程能产生看起来完整的文件，但选择、关系、综合和传递都没有统一机器可读的中间事实。既有诡异屋项目的资料调用审计已经明确写出：`MOD-CONNECTION`、`MOD-STATIC`、`MOD-EXECUTION` 属于 `called_not_transformed`，`CAP-DESIGN-TO-DRAFT` 属于 `retrospective trace only`。这正是用户描述现象的直接证据，而不是推测。

## 3. 根因与因果关系

### 根因 A：索引是登记表，不是任务规划器

索引记录了 `path`、`dimensions`、`call_when` 和 `related`，但原系统没有执行解析、评分、去重、依赖排序或证据选择。结果是“按索引选择”依赖模型临场判断，任务变化不会稳定改变调用集合。

### 根因 B：模块没有统一输出协议

资料组合机制定义了能力、类型、静态、动态、锚点和执行模块的职责，但没有强制每个模块产出同构的 `inputs / evidence / decisions / conflicts / writing_requirements / acceptance_criteria`。多份资料因此只能并列出现，不能形成可合并的中间对象。

### 根因 C：关系是文字说明，不是可传播的边

`related` 关系存在于 YAML，状态变化存在于快照，章节要求存在于 JSON，但三者没有同一轮的交接 ID。前一阶段的判断只能通过 Cline 记忆或手工复制继续传递，剧情变化也不能自动成为下一轮资料选择条件。

### 根因 D：正文验证是存在性检查，不是影响证明

旧检查器不读取正文与执行清单之间的证据映射，也不计算“来源 -> 决策 -> 设计 -> 文本 -> 状态”的完整链。项目审计中的 `retrospective_reconstruction` 和 `PASS_WITH_REPAIR_GAPS` 证明设计产物是在正文之后补建，不能证明生成前真正影响正文。

### 根因 E：状态契约存在，但没有执行门

状态契约定义了剧情轮次、角色状态、世界反应和保存门禁，这是正确方向；但它以前只是被 Cline 遵守的文本规范。没有工具强制 `Plan`、`Verify` 和失败状态写入，因此状态可保存不等于状态真的驱动了后续生产。

## 4. 表面症状与根因区分

| 表面现象 | 实际原因 |
|---|---|
| 资料很多却只用少量内容 | 没有任务相关性选择器和证据包 |
| 多模块同时读取但结果单薄 | 没有统一综合输入/输出和冲突裁决对象 |
| 前章结果无法影响后章 | 没有稳定的状态交接链和下一轮上下文构建 |
| `source_trace` 很完整但作用不明 | 只记录来源 ID，没有中间决策和正文定位的强关联 |
| 检查报告通过 | 检查器验证结构存在，不验证行为闭环 |
| 大文件难以使用 | 只有 `read_mode` 约定，没有可复用的局部证据提取结果 |

## 5. 重构后的实际运行方式

每轮按以下闭环运行：

`任务上下文 -> Plan -> 证据包 -> 综合决策 -> 章节设计 -> 执行清单 -> 正文 -> 状态更新 -> Verify -> 下一轮上下文`

`运行资料闭环.ps1` 现在负责：

- 只从当前工作区索引和 `08_原始资料` 解析来源，明确禁止外部路径；
- 读取项目元数据、快照、启动参数和最近章节作为实时上下文；
- 根据任务词、维度、必选标记和优先级生成选中/未选模块及理由；
- 将 `related` 转为依赖边，并输出固定执行顺序；
- 从实际原始资料提取有限证据片段，形成 `influence_contract`；
- 规定综合输出必须包含决策、冲突、状态变化、写作要求、来源追踪和未采用理由；
- 规定设计到正文的交接链，并在 `Verify` 中区分 `PASS`、`PARTIAL` 和 `FAIL`。

这不是把原始资料拼成更长提示词，而是把资料变成一组带输入、输出、依赖和影响证明的执行节点。

## 6. 已重新建立的关系

1. 类型/风格/篇幅参数 -> 任务上下文和模块相关性。
2. 能力与类型 -> 类型连接 -> 静态结构。
3. 静态结构 -> 动态因果与状态传播。
4. 动态因果 + 当前人物状态 -> 场景锚点和章节行动。
5. 所有模块 -> 综合决策 -> `chapter_execution_manifest`。
6. 正文结果 -> 角色认知、世界反应、剧情轮次和下一章问题。
7. 每个来源 -> 证据片段 -> 决策字段 -> 设计要求 -> 正文证据 -> 检查结果。

## 7. 状态持续传递

项目快照仍是项目事实的权威来源，正文仍不可覆盖。新增运行产物不替代快照，而是为每一轮生成可复核的上下文和影响契约。下一轮必须读取快照的 `chapter_state`、连续性字段、最近正式章节和上一轮验证结果；剧情轮次的八个字段（问题、目标、障碍、行动、后果、新信息、状态变化、新问题）继续由状态契约约束。

## 8. 验证与边界

已有项目是修复前生成的真实样本，审计明确其部分产物为事后重建，因此不能把它 retroactively 宣称为完整闭环。本轮验证的标准是：新运行必须能生成机器可读计划；选中来源必须存在；必须有关系边和影响链；Verify 必须对缺失的生成前交接返回 `PARTIAL` 或 `FAIL`。这会主动暴露旧项目的证据缺口，而不是用静态 PASS 掩盖它。

剩余限制：PowerShell 工具能可靠完成结构化编排和证据审计，但不会替代语言模型进行语义综合，也不会把纯文本原始资料自动变成完整故事事实。原始资料编码异常仍需按索引标记处理。下一次真实章节生产必须使用 `Plan` 产物作为生成输入，并在正文保存前执行 `Verify`。
