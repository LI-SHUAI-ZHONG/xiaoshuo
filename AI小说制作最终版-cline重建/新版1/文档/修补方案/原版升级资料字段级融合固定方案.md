# 原版升级资料字段级融合固定方案

## 1. 唯一方向

本方案固定“原版资料与升级资料改进融合”的执行方向。原版资料是历史基线，升级资料是可验证的改进证据；二者必须按对象、按字段对照后生成新的融合资料版本。不得把升级资料降级为仅索引，也不得把能够进入资料本体的改进停留在项目消费记录中。

本方案是《全量资料模型受控改进最新版方案》和《配置/全量模型资料改进方案.json》的强制补充。废止“原始资料不可改写”的旧约束：原版资料是需要被升级为最终版本的工作资料，字段级融合通过后必须受控写回对应原版资料。写回前必须保留可恢复的原版快照、前后哈希和完整变更账本；既有绑定和已签核证据不被静默覆盖，需随新资料版本重新关联。

## 2. 四层结果必须分开

每次融合必须输出以下四层结果，并使用共同的 `object_id` 关联：

1. `material_fused`：原版对象与已验证升级字段组成的最终资料本体。资料定义、结构、依赖、边界、示例、规则和完整使用方法都必须进入这里，并在通过写回门后回写对应原版资料文件。
2. `validated_overlay`：同源派生改进或尚未达到正式事实融合门的已验证语义单元。它不覆盖原版，也不得自动晋升为 `material_fused`。
3. `index_derived`：便于检索、分类、定位和统计的派生索引。索引字段不得冒充资料本体事实。
4. `project_consumption`：项目采用、场景绑定、正文位置、文学审校和消费结果。该层不得写入资料本体定义。

场景绑定、`text_location`、采用状态、文学审校结论、替代授权和隔离审计结论属于项目消费或治理证据；项目消费不得写入资料事实。

`resolved_material_view` 只作为写回前的预览和失败批次的临时读取视图。正式完成后，主创作流程默认读取已写回的最终原版资料，并记录 `material_version`、资料文件 SHA-256 和写回批次 ID；不得继续把旁路视图当作最终资料替身。

升级内容的状态晋升固定为：`candidate -> validated_overlay -> validated_fused -> written_back_final_material`。只有满足正式字段融合全部证据门、完成原版资料写回、前后哈希校验和回读验证后，才可标记为 `written_back_final_material`；不得因绑定记录、正文消费或解析视图可读取而自动晋升。

## 3. 对象匹配规则

融合前必须先建立原版对象与升级对象的对应关系，禁止按文件时间、目录名称或候选摘要直接合并。匹配优先级固定为：

```text
稳定 object_id / entry_id / type_id / connection_id
> 原版 source_ref 与规范化标题
> 唯一名称、板块和类型组合
> 内容指纹相似度
> 人工或模型候选匹配
```

匹配状态固定为 `exact_match`、`probable_match`、`new_object`、`unresolved`。只有 `exact_match` 和完成对象级哈希、来源、结构校验的 `probable_match` 可以进入字段裁决；`new_object` 可作为新增对象进入融合版本；`unresolved` 必须保留为待处理，不得强行并入。

`binding_id` 只表示绑定记录，不自动等于资料对象身份。类型连接等重复绑定必须使用来源区段、对象序号和稳定字段组成 `canonical_object_id`。

## 4. 语义字段与规则单元裁决

不得把升级资料抽象为“新增内容”或对数组做无条件追加。升级对象必须先按资料类型解析为语义字段和规则单元，再进行裁决。至少区分以下单元：

```text
scalar              定义、名称、状态、优先级等单值字段
set_member          标签、包含项、排除项、示例等无序集合成员
relation            依赖、静态边、类型连接等有方向关系
condition           前置条件、适用条件、触发条件、失效条件
effect              触发后的状态变化、传播、结果和代价
constraint          时间线、空间、身份、资源和写作限制
exception           例外、失败分支、替代分支和禁止假设
guarantee_boundary  not_guaranteed、候选效果与实际结果的边界
structure           对象层级、规则块、分支结构和字段组织
```

每个语义单元必须记录 `unit_id`、`unit_kind`、`field_path`、稳定键、原值、候选值、来源、推导规则和校验结果。规则的条件、效果、约束和例外不得被拼接成一段文本后再合并。

每个语义字段或规则单元必须单独产生一个动作：

```text
retain       保留原版
correct      用有证据的升级值修正原版
complete     原版缺失，由升级证据补全
extend       在同一语义集合中追加已验证成员
restructure  按 schema 调整规则/条件/分支结构，同时保留原值和变更记录
conflict     两方冲突，暂不自动裁决
```

默认不删除原版字段。`remove` 只有在升级证据明确证明原版错误或失效、且通过结构和依赖回归后才允许；否则使用 `conflict`，不得静默覆盖。

字段分类固定为：`identity`、`definition`、`relation`、`condition`、`effect`、`constraint`、`exception`、`guarantee_boundary`、`structure`、`example`、`status`、`source_ref` 和 `project_consumption`。除 `project_consumption` 外，前述资料语义字段都可以按证据进入 `material_fused`；但必须保留其结构角色，不能因为可以进入资料本体就按普通数组处理。

### 4.1 资料类型的语义键

```text
资料库 relation:
  entry_id + dependency.entry_id + dependency.type

静态网络 relation:
  source + target + type
  condition、priority、mainline_level 是关系属性，不是项目消费

动态网络 rule:
  normalized_id 或 source + target + type + condition
  direction、strength、valid_types、effect、priority、failure_branches、not_guaranteed 必须分别校验

类型连接 object:
  dynamic_combination_id
  dynamic_rule_ids、trigger_condition_ids、candidate_effect_ids、selection_constraints、
  continuity_constraints、failure_branches、alternative_branches、forbidden_assumptions、
  not_guaranteed 为不同语义集合

锚点网络 object:
  anchor_id/category/name + definition/conditions/translation_boundary
```

同一关系键下，条件、效果、约束或保证边界不一致时，不得使用 `extend` 掩盖差异，必须生成 `conflict` 或 `restructure`。

## 5. 证据门

升级字段进入 `material_fused` 前必须同时满足：

1. 原版对象可由 `source_ref` 回读，原版对象哈希与基线一致。
2. 升级对象有明确来源、来源哈希和派生规则。
3. 原版对象与升级对象的身份匹配已验证。
4. 候选字段符合对应 source kind 的 schema 和必填字段规则。
5. 候选内容不是项目事实、场景结果、正文位置或仅凭模型推断生成的事实。
6. 依赖、稳定 ID、规则语义键、条件兼容性、效果适用范围、重复项和跨对象冲突检查通过。
7. 变更账本记录原值、候选值、合并值、证据定位、双哈希和裁决动作。

只有摘要、语义锚点、采用记录、文学审校或授权记录的候选，不得直接进入 `material_fused`。它们可以保留在对应的索引、治理或消费输出中。

## 6. 证据等级和动作

```text
A direct_merge       对象、来源、哈希、schema 和冲突均通过，直接融合
B verify_then_merge  有明确改进价值，但仍需补对象/来源/依赖验证
C index_only         可改善检索或分类，但不足以修改资料事实
D consumption_only   属于项目采用、场景、正文、审校或治理证据
```

等级 A 进入当前融合批次；等级 B 进入验证队列；等级 C 进入 `index_derived`；等级 D 进入 `project_consumption` 或治理证据。任何等级都不得丢弃原始内容和追溯路径。

## 7. 固定执行顺序

```text
冻结原版基线
-> 回读并哈希原版对象
-> 解析升级对象
-> 建立 canonical_object_id 映射
按 source_kind 解析语义字段、关系和规则单元
-> 按稳定语义键生成差异
-> 字段级证据裁决
-> 生成 material_fused、resolved_material_view、index_derived、project_consumption
-> 依赖/来源/隔离/重复/冲突回归
-> 输出 merge preview 和正式变更集
```

融合版本使用新版本号和新批次 ID，至少包含：

```text
manifest.json
融合资料对象文件
resolved_material_view/（供模型和项目读取的版本化资料视图）
field_changes.jsonl
unresolved_conflicts.jsonl
merge_preview.json
```

原版快照、升级候选、融合结果和变更账本均采用追加式证据保存。原版资料文件允许被当前最终版本更新，但每次更新都必须保留旧快照、旧哈希、写回批次和可回滚路径；禁止覆盖旧运行、旧版本或已签核证据。

## 8. 各资料类型的边界

- 资料库：可融合定义、写作/设计指令、条件、范围、依赖、示例和限制；项目采用不能伪装成通用示例。
- 类型系统：可融合类型定义、核心元素、包含/排除项、混淆项和规则；项目选择不写入类型本体。
- 类型连接：可融合兼容机制、冲突、条件、风险和 `not_guaranteed`；项目激活状态单独保存。
- 静态网络：可融合稳定关系、制度/地点/势力/资源约束和原创风险；具体场景位置单独保存。
- 动态网络：可融合触发条件、状态变化、传播和反馈规则；一次项目发生不证明通用规则必然发生。
- 锚点网络：可融合定义、分类、适用条件和转译边界；正文位置与审校结果单独保存。

## 9. 完成条件和禁止事项

一次正式融合只有在以下条件全部满足时才完成：对象映射可追溯；每个语义字段/规则单元有裁决动作；所有 `merged` 变化有来源和双哈希；条件、效果、约束和例外的结构角色未丢失；冲突显式保留；新增对象身份唯一；依赖闭合；规则条件可满足性和适用范围检查通过；原版哈希未漂移；资料视图与项目消费没有越界混写；merge preview 与正式变更集一致。

禁止：升级资料整体覆盖原版；无字段裁决地整段拼接；以摘要代替原始对象；把一次项目消费伪装成通用事实；把授权当作事实确认；把文学审校当作资料来源；因类型尚未项目确认而排除类型资料的通用改进；因资料存在于索引而自动认定已写回。允许并要求对通过证据门的字段、规则和使用方法受控写回原版资料。

## 10. 固定验收问题

每次运行结束必须能逐条回答：

```text
这个升级字段对应哪个原版对象？
它改变了哪个字段？
为什么是 retain/correct/complete/extend/restructure/conflict？
原版和升级对象的来源及哈希在哪里？
它进入了 material_fused、index_derived 还是 project_consumption？
冲突、未决和未支持字段是否仍被明确保留？
```

无法回答任一问题的候选不得进入正式融合资料版本。
