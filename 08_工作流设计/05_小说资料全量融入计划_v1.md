## 4. 运行合同和强制门

每个单元记录来源 ID、文件与片段哈希、字节/行区间或 JSON 对象路径、原文角色、旧 ID、版本和重复/替代关系、功能、适用及排除条件、依赖、阶段、产物字段、证据类型和问题 ID。JSON 位置同时保存对象 ID 和索引，避免重排后误引。原文、旧升级和新解释须可回查。

| 维度 | 状态和证据 |
|---|---|
| 入库覆盖 | indexed、quarantined、missing、alias、reference_only。以源段、文件缺口或有依据的排除对账 |
| 解释与路由 | needs_review → routed。逐项写清原义、功能、触发、依赖、产物与检验点 |
| 执行资格 | candidate、trial、approved、suspended。必用性来自来源、适用条件、作者选择及上游依赖；旧授权和模型自评不能提升资格 |
| 本次采用 | required、selected、not_applicable、deferred、blocked。绑定用途、阶段、版本及理由；必用项不受 0–5 张可选方法卡限额影响 |
| 执行证明 | design_verified、prose_verified、state_verified，或 unverified/failed。流程规则可凭真实执行记录验收，类型承诺和写法分别查设计及正文，不能用“已读取”替代 |

1. **Brief → 类型 → 类型连接。** 解析作者要求和未定事项；冻结候选的来源及约束，再让模型提出解释或应用。缺必用依据在模型调用前阻断。每个设计声明必须来自已知项目事实、作者决定、资料依据或标明的原创候选。
2. **世界/人物 → 卷章 → 场景。** 绑定静态端点，核对动态的触发及前后状态，给锚点绑定可观察时机。把资料库的参数转为设计字段和检查点。模型在已确认边界内提出具体表现，不能填补资料缺失；关键原创候选由作者确认后才成事实。
3. **写作 → 独立审稿。** 冻结实际发送内容、规则版本、依赖和证据合同；按 POV 与时点裁剪知情。每条必用检查回传通过、失败或未验证，并附定位与理由。结构用确定性检查，语义要查段落及实际效果，争议交作者；不能只凭关键词、名称或资料 ID 判通过。
4. **修订 → 接受 → 续写。** 证据绑定同一草稿 ID、版本、段落范围和哈希。改稿重验受影响规则；接受事务核对冻结规则、决定、正文、证据和故事基线，原子推进接受指针及状态。来源修订只标出受影响后续，历史快照仍可查。

**验收例：** 静态网络第一条把「主角」与「核心悬念」绑定；动态网络 C00001 以本项目已经采用该静态关系为条件。设计器先查两端在本项目分别指什么，再要求把悬念推进绑定到该角色的具体选择和代价，写前记录预期影响谁的知情。锚点只能用已可见的动作或物件表现这一变化；审稿要定位支持该选择和状态变化的段落。只让角色出场、在文本里提及悬念、或在计划里预写后续知情，均不能给动态链计通过。如果本项目未采用该关系，动态链应有未适用理由，不生成项目事实。

问题统一登记问题 ID、来源定位和哈希、缺陷类型、可信度、影响范围、证据、修订提议、状态及裁定。缺失或冲突的硬规则必须返回原因、受影响节点及候选替代，不许退回无规则路径。可选缺陷延后并记录理由。修复以有来源的恢复件或新解释覆盖层发布，保存前后差异、决定、适用范围及回归。
