# 执行 22：可观测性、韧性、备份与灾备

## 任务目标

让系统可诊断、可限流、可恢复：贯通 API/Workflow/Agent/Model/存储的日志、指标和 Trace，完成数据库与对象存储的备份恢复、项目导出及故障运行手册。

## 前置条件

- 执行 21 通过；核心功能关闭扩展后仍稳定。
- 只允许在本地/测试环境做破坏性恢复演练。

## 本阶段实施

1. 统一结构化日志字段：timestamp、level、service、environment、request/trace/workflow/task/agent/model call ID、workspace/project 脱敏引用、event、duration、outcome、error code。
2. 接入 OpenTelemetry 端口与 OTLP 可选导出；本地提供可观测性 Compose profile。未启用导出时应用不得失败。
3. 建立低基数指标：API 延迟/错误、Worker 队列/租约、Workflow 状态、Outbox 延迟、模型用量/故障切换、数据库池、知识摄取、SSE 连接、对象存储错误。
4. 定义初始 SLI/SLO 与告警条件，明确这只是框架基线，不用虚假生产数据宣称达标。
5. 对外部调用统一设置 timeout、有限 retry、backoff、circuit breaker、bulkhead/并发限制和 rate limit；相关值集中配置并有测试。
6. 创建安全扫描与运行检查：依赖审计、容器非 root、只读文件系统可行性、最小网络暴露、上传限制、日志脱敏、Secret 不入镜像。
7. 建立 PostgreSQL 备份/恢复脚本、对象存储版本/清单、Redis 非权威恢复说明；备份包含 schema/app 版本和校验和。
8. 建立 Workspace/Project 导出 manifest：权威数据、资产引用、版本、审计和校验；导入先验证兼容性和冲突，不直接覆盖。
9. 在隔离临时环境执行“备份 -> 破坏技术测试数据 -> 恢复 -> 完整性校验”；记录 RPO/RTO 目标和实际演练时间。
10. 编写依赖故障、磁盘不足、队列堆积、迁移失败、对象缺失、回滚与恢复 runbook；写入 `docs/handoffs/22.md`。

## 本阶段不做

- 不对真实/生产数据执行破坏演练，不自动删除备份。
- 不将正文、Prompt、Memory 内容、密钥或完整用户 ID 放入指标/日志。
- 不自动部署到云，不购买监控服务。

## 验证

- 一次 UI 操作可用 trace/correlation ID 追到 API、Workflow、Agent、Model Call、Outbox 和存储结果。
- 故意触发超时、熔断、队列不可用、对象存储不可用，系统进入可诊断状态且不丢权威数据。
- 临时环境备份恢复后，项目、Revision、任务、审计、对象清单和校验和一致。
- 未配置 OTLP 时本地栈正常；启用后 Trace/Metric 可见且脱敏。
- 容器、依赖、配置和秘密检查通过；恢复脚本要求显式目标且拒绝宽泛路径。

## 完成标准

- 系统具备可重复的观测、故障定位、备份、恢复和导出证据。
- `docs/handoffs/22.md` 标记 `PASS`，附最近一次隔离恢复演练结果。
