# 何时允许拆分服务

## 默认立场

模块保持在 `services/core/` 模块化单体内。技术偏好、愿景图中的 Service Mesh 或“未来可能扩展”都不是拆分依据。拆分必须同时通过下述运行证据和就绪门槛，并由新 ADR 批准。

## 运行证据门槛

候选模块需要至少连续 8 周的代表性生产遥测，并满足以下至少两项：

1. **独立扩缩容**：候选模块在连续 4 周内至少有 3 个峰值窗口达到 CPU、内存、连接或队列资源的 70%，而 Core 其余部分低于 40%；容量模型证明独立扩缩容可降低至少 30% 计算资源或消除 SLO 违约。
2. **延迟/吞吐隔离**：候选负载导致 Core API 或 Worker 的既定 p95/p99 SLO 在 4 周内至少 3 次违约，隔离压测证明拆分可恢复目标且不会把瓶颈转移到数据库或网络。
3. **故障隔离**：候选模块在 90 天内造成至少 2 次影响其他模块的 Sev-1/Sev-2 事件，故障注入证明进程/部署隔离能显著缩小影响面。
4. **发布独立性**：候选模块与 Core 在 8 周内发生至少 4 次相互阻塞的发布，并且独立发布可减少至少 50% 等待时间；阻塞证据来自 CI/CD 与变更记录。
5. **合规或数据区域**：有书面法规、合同或数据驻留要求，单体部署无法在不扩大受限数据范围的情况下满足。

## 必须全部满足的就绪门槛

- 模块有唯一团队/负责人、服务目录条目、值班和容量责任。
- 数据所有权已单一化；不存在跨模块共享可写表、数据库触发器或跨库事务依赖。
- 同步 API 和异步事件均版本化，有消费者契约测试、幂等语义、超时和退避策略。
- Outbox/Inbox 或等价可靠交付已通过重复、乱序、延迟和丢失测试。
- 已定义独立迁移、备份、恢复、数据校验和回滚方案，并完成一次演练。
- 已定义 SLO、指标、日志、追踪、告警和故障预算；关联 ID 可以跨网络边界传播。
- 授权、工作区隔离、审计、密钥和最小网络权限有正向与反向安全测试。
- 在代表性负载下完成影子或双读验证，量化延迟、可用性、成本和运维增量。
- 新 ADR 记录边界、证据、替代方案、迁移顺序、失败回滚和是否真的需要 Service Mesh。

## 拆分步骤约束

1. 先在单体内消除私有表和实现导入，形成稳定公共契约。
2. 引入可观测的远程适配器，但保持本地适配器可回滚。
3. 迁移只读流量并校验结果，再迁移写入所有权。
4. 在至少一个完整回滚窗口内保留可验证的回退路径。
5. 完成后删除旧写路径和临时双写；禁止永久双主。

## 明确不能作为理由

- “微服务更现代”或组织希望使用某项基础设施。
- 模块代码行数、目录数量或概念上可独立。
- 尚未测量的未来规模。
- 单个慢查询可以通过索引、批处理或异步化解决。
- 为引入 Kubernetes、Service Mesh、独立图数据库或向量数据库而反向制造边界。
