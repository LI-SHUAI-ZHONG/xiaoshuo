## 本阶段变更

### Workflows 领域与应用契约

- 新增 `modules/workflows`：版本化 `WorkflowDefinition`/`StepDefinition`、`WorkflowRun`、`StepRun`、`TaskRun`、审批请求/决定、运行事件、仓储/执行器端口、应用服务与 Worker handler。
- Workflow 是长任务的唯一调度者。后续 Master、Director 或 Agent 只能经公开 Workflow 用例提交、控制或查询运行，不能绕过模块边界直接写其他模块私有状态。
- Run 状态覆盖 `pending`、`running`、`paused`、`waiting_approval`、`succeeded`、`failed`、`cancelling`、`cancelled`；所有非法迁移由统一状态规则拒绝，三个终态不可继续迁移。
- Task 保存 attempt、available/deadline、输入/输出/错误引用、稳定幂等键、租约 token/expiry 和最后投递事件 ID；Step 保存 attempt、deadline 与引用。
- 提交使用 Workspace + 定义维度的幂等记录：同键同请求返回原 Run，同键不同请求摘要拒绝。所有查询和控制都执行 Workspace/Project scope 与现有 RBAC/审计契约。
- 人工审批必须显式请求、显式过期和由另一名人类 actor 决定；请求者不能批准自己，非用户主体不能决定，不存在默认或自动批准。
- 每个 Run 的版本化事件 sequence 从 1 严格递增，并支持 `after_sequence` 查询，为执行 16/17 的 REST/SSE cursor 预留稳定契约。

### 持久化、Outbox、队列与恢复

- 新增 Alembic revision `0004_workflow_engine` 和八张表：`workflow_definitions`、`workflow_step_definitions`、`workflow_runs`、`workflow_step_runs`、`workflow_task_runs`、`workflow_approval_requests`、`workflow_approval_decisions`、`workflow_run_events`。
- 定义、步骤定义、审批决定和运行事件由数据库 trigger 保持 append-only；业务状态、运行事件和 `workflows.task-dispatched` Outbox 记录在同一事务中提交。
- 新增 `SqlAlchemyWorkflowRepository`，用行锁、唯一约束、租约 token 和版本字段保护重复投递、并发控制、租约过期恢复与结算。PostgreSQL 是唯一事实源。
- 新增 `CeleryEventPublisher`、JSON envelope 编解码、`accos.workflows.consume` consumer 和 `InMemoryTaskQueue`。Celery 配置 late ack、worker-lost reject、prefetch 1、JSON only、禁用 result backend；consumer task 使用 `shared=False`，防止同一进程中多个 Celery app 的同名 handler 污染。
- 执行 05 的 `OutboxRelay` 已接入 Worker 进程。队列发布失败只更新 Outbox 的有界重试时间；恢复 Redis 后继续发布，发布确认前崩溃允许重复事件，由数据库 Task 状态和租约去重。
- Worker 的 Relay 使用主 Selector event loop，Celery `solo` consumer 使用工作线程。consumer 有独立 `NullPool` 数据库 runtime，避免跨线程/跨事件循环复用主异步连接池。
- 活动租约期间的重复投递被忽略；租约过期后新 Worker 可重新认领并递增 attempt。执行中取消优先进入 `cancelling`，即使执行器随后成功、失败或超时也先补偿并结算为 `cancelled`。
- 重试采用有限指数退避。通用默认值为最多 3 次、1 秒起步、2 倍增长、60 秒封顶；`framework_smoke` 为最多 3 次、1 秒起步、2 倍增长、8 秒封顶，每次尝试 timeout 10 秒，Worker 租约 30 秒。
- 重试耗尽或永久错误使 Task 进入 `dead_letter`，Step/Run 进入失败终态；补偿 Hook 失败保存稳定 `workflow-error://compensation-failed`，未知异常不泄漏内部详情。

### 纯技术烟雾工作流与进程组合

- 新增 `framework_smoke` v1：只传递 `fixture-token://` 技术引用，执行一次受控失败重试和 10 ms 可控延迟，输出确定性元数据引用；不生成任何创作内容。
- Fake 队列与真实 Redis/Celery 复用同一 Workflow/Worker 契约测试；真实链路验证四次投递（含一次受控重试）后到达 `succeeded`。
- composition root 注册 WorkflowService、SQLAlchemy repository、FrameworkSmokeExecutor、Outbox Relay、Celery app/consumer 与独立 consumer database runtime。
- Worker 入口现在同时运行唯一 Relay 和 Celery consumer，启动日志为 `registered_tasks=1`，任务列表包含 `accos.workflows.consume`；模块生命周期会同时管理主数据库与 consumer 数据库。
