# 执行 08：事件、任务与工作流引擎

## 任务目标

建立 ACCOS 唯一的长任务调度机制：持久化 Workflow/Run/Step/Task 状态，支持幂等、重试、超时、取消、暂停、恢复和人工审批，并用纯技术烟雾工作流证明 Worker 中断后可续跑。

## 前置条件

- 执行 07 通过。
- Redis、PostgreSQL、API 与 Worker 可同时启动。

## 本阶段实施

1. 创建 `workflows` 模块，至少包含：
   - 版本化 `WorkflowDefinition` 与 `StepDefinition`；
   - `WorkflowRun`、`StepRun`、`TaskRun`；
   - 状态机：pending/running/waiting_approval/succeeded/failed/cancelling/cancelled；
   - attempt、deadline、retry policy、idempotency key、input/output reference、error reference。
2. Workflow 是唯一调度者；未来 Master/Director 只能选择或规划 Workflow，不能直接跨模块任意写数据。
3. 实现 Celery 队列适配器、Worker 队列消费者和内存 Fake；业务状态始终写 PostgreSQL，Redis 不是事实源。
4. 执行 05 的 `OutboxRelay` 负责“数据库 Outbox -> Redis 队列”的发布、游标和确认；本阶段 Worker 只消费队列并更新持久化 Run/Task。两端按 at-least-once 语义，通过事件 ID、任务幂等键、唯一约束和租约防止重复副作用。
5. 实现指数退避上限、最大次数、超时、取消检查、暂停/恢复、死信/人工处理状态和补偿 Hook。
6. 创建纯技术 `framework_smoke` 工作流：只传递固定技术 token、执行可控延迟/失败步骤并保存元数据，不生成内容。
7. 建立人工审批 Step 协议：请求、决定、actor、理由、过期和审计；默认不能自动批准。
8. 发布版本化运行事件，为执行 16 的 SSE 预留递增序列号。
9. 添加状态机、崩溃恢复、重复投递和取消测试；写入 `docs/handoffs/08.md`。

## 本阶段不做

- 不嵌入写作、研究、世界或人物工作流。
- 不把 Celery result backend 当作唯一状态库。
- 不允许无限重试、无预算循环或由浏览器连接决定任务生死。

## 验证

- 所有非法状态迁移被拒绝，合法路径有状态机测试。
- 同一任务重复投递只产生一个业务结果；同一幂等键重复提交返回原 Run。
- Worker 在步骤中断后重启，Run 能按租约/重试策略恢复。
- 超时、失败、取消、暂停、恢复、待审批和审批拒绝均进入明确终态并有审计。
- Outbox 与队列暂时不可用时不丢任务；恢复后可继续发布。
- `framework_smoke` 在 Fake 队列和真实本地队列上通过同一契约测试。

## 完成标准

- 技术烟雾工作流可从应用用例提交、由 Worker 执行并在进程重启后查询终态；正式 HTTP 路由统一在执行 16 暴露。
- `docs/handoffs/08.md` 标记 `PASS`，记录状态图、重试默认值和恢复操作。
